# v1.0 Production Handoff

**Audience:** an external DevOps/SRE agency (deployment + capacity) and an
independent security firm (external review). This document is the work order for
taking CTFGenerator from *code-complete, internally validated at simulation scale*
to a **signed v1.0**.

**What "done" means:** every box in [`docs/RELEASE_CRITERIA.md`](../RELEASE_CRITERIA.md)
§ v1.0 is checked against **real, re-runnable evidence**, and the adjudication in
[`docs/RELEASE_QUALIFICATION.md`](../RELEASE_QUALIFICATION.md) shows no
`NOT-QUALIFIED` / `PENDING` v1.0 rows. There is **no remaining application code**
to write — the gaps are all *deployment*, *scale*, *external-party*, and
*process* items. If you find yourself changing `src/`, stop and talk to the
maintainer: it almost certainly means a constraint below was misread.

---

## 0. Non-negotiable constraints (read first)

These are load-bearing security invariants. Violating one silently fails the
release, regardless of what else works. They are enforced/asserted in code and in
CI; your deployment must not undo them.

1. **The control plane never executes challenge code and never mounts a container
   socket** (ADR-001 / gate **S9**). The API/web/worker-gateway containers get
   **no** Docker/Podman socket. Only workers run challenge containers. See
   [`docs/security/threat-model.md`](../security/threat-model.md).
2. **Workers run on separate hosts from the control plane**, on a **rootless**
   engine with `NET_ADMIN` (for the host-block firewall floor). A worker without
   that floor **refuses to launch** — do not "fix" that by loosening it. See
   [`docs/security/runtime-isolation.md`](../security/runtime-isolation.md) and
   `deploy/Dockerfile.worker`.
3. **The worker gateway is a disjoint trust plane** from the human API. It carries
   only scoped worker tokens, wires no human routers, and must **not** be exposed
   on the public human edge. See `deploy/docker-compose.worker-gateway.yml`.
4. **Secret-free everywhere.** Secrets live only in the environment / `.env`
   (gitignored) / your secrets manager. Flags, tokens, and provider keys are never
   logged (gate **S5**) — keep it that way in any log shipping you add.
5. **Append-only tables stay append-only** (`audit_events`, the ledger,
   `job_transitions`, published content) — enforced by DB triggers. A restore must
   *load* rows, never mutate them (gate **S8**).

## 1. System shape (what you are deploying)

Three planes, deliberately isolable:

| Plane | Process | Image | Holds |
|---|---|---|---|
| **Control plane — human** | `uvicorn …api.app:app` (`MODE=api`) | `deploy/Dockerfile.api` | DB DSN, session keys, artifact store |
| **Control plane — worker gateway** | `uvicorn …api.worker_app` (`MODE=worker-gateway`) | same image | DB DSN; **no** socket |
| **Execution plane — worker** | `ctfgen-worker` | `deploy/Dockerfile.worker` | scoped token + gateway URL + **rootless docker socket** |
| **State** | PostgreSQL 16 | `postgres:16` | source of truth |
| **Ingress** | Caddy (TLS) | `caddy:2` | proxies **only** the human API |

Reference topologies already in-repo (`deploy/`):

- `docker-compose.yml` — single-host control plane (postgres + api + Caddy).
- `docker-compose.worker-gateway.yml` — adds the worker-gateway listener.
- `docker-compose.worker.yml` — the execution-plane worker host (separate host).
- `docker-compose.pitr.yml` — WAL-archiving overlay for PITR.
- `Caddyfile` — TLS termination + hardened headers.
- `.env.example` — every variable, with placeholders. **Copy to `.env`, fill real
  values** (it is gitignored).
- `entrypoint.sh` — migrate-then-serve, fail-closed; `verify-deploy.sh` — smoke.

These are **reference** compose files (they say so): production may want
Kubernetes/Nomad/systemd instead. The *shape* (three planes, the constraints in
§0) is what must hold — not compose specifically.

## 3. Work items

Each item lists the **objective**, **what already exists**, **do**, and the
**acceptance gate** (how you prove it — the release-criteria box it closes, and
the executable/artifact that must show green). Do them roughly in the order below;
item 1 unblocks the measurement in 2, 4, 5.

### Item 1 — Stand up the production deployment (TLS + multi-host + object storage)

*Closes:* RELEASE_CRITERIA "Supported single-path deployment", "TLS-terminated
ingress", and QUALIFICATION blocker #2.

- **Exists:** `deploy/*` (§1), `docs/HOSTING.md`, `docs/operations/configuration.md`.
- **Do:**
  1. Provision: 1+ control-plane host, 1+ **separate** worker host(s) with a
     rootless engine + `NET_ADMIN`, managed PostgreSQL 16, and artifact storage
     (local-FS **or** S3-compatible — set `CTFGEN_ARTIFACT_ROOT` or wire the S3
     backend).
  2. Real DNS + TLS: point `PUBLIC_DOMAIN` at the Caddy host; let Caddy ACME-issue
     the cert (or front with your own LB — keep TLS termination + the hardened
     headers from `deploy/Caddyfile`).
  3. Bring up control plane (`docker-compose.yml` + `…worker-gateway.yml`), then
     worker host(s) (`docker-compose.worker.yml`) pointed at the gateway URL with
     their scoped tokens.
  4. Seed the first admin **once, by hand**: `ctfgen-admin bootstrap-admin`
     (reads `CTFGEN_BOOTSTRAP_ADMIN_PASSWORD`). Never auto-run it.
  5. Run `deploy/verify-deploy.sh` and confirm `/api/v1/system/ready` is green
     (it goes green only after migrations reach head).
- **Acceptance gate:** the human API reachable **only** over TLS; session cookies
  `Secure`; worker gateway on a private interface (not the public edge); a worker
  on a separate host successfully claims a job and launches a challenge container
  through the gateway. Capture the topology + a successful joined-flow run as
  evidence.
- **Constraints:** §0.1–§0.4. The control-plane hosts must have **no** container
  socket; the worker host's socket is **rootless**.

### Item 2 — Production-scale capacity run (25 teams × 20 challenges, sustained)

*Closes:* "25 concurrent teams; 20 active challenges", "scoreboard <3 s /
submission <500 ms server-side sustained", QUALIFICATION blocker #1.

- **Exists:** `scripts/loadtest.py` (measures submission p95, scoreboard lag,
  launch-success proxy); [`docs/validation/capacity.md`](../validation/capacity.md)
  (targets + the in-process GIL caveat).
- **Context you must respect:** the in-process harness measured submission p95
  ≈ 2050 ms at 25×20 — but that was shown to be a **GIL-bound single-interpreter
  artifact** (app + DB + load-gen in one process), *after* the two real product
  ceilings were fixed (submission advisory-lock grain narrowed to
  `(competition, team, version)`; connection pool sized above the request-thread
  count). Your run must be **multi-process / multi-host / out-of-process load
  generation** against the real deployment so the number reflects the product,
  not the harness.
- **Do:** drive the real API from an **external** load generator (locust/k6/your
  own) at 25 steady-state teams × 20 live challenges; record submission p50/p95/max
  (server-side), scoreboard update lag, and launch success. Sustain it (not a
  spike) long enough to be representative.
- **Acceptance gate:** submission p95 **< 500 ms server-side**, scoreboard update
  **< 3 s**, **≥ 99 %** instance-launch success — all **sustained** at 25×20.
  Publish the run config + measured numbers (the tracker requires real numbers,
  not claims).

### Item 3 — Real external closed beta

*Closes:* "A real competition run at target scale", "Beta findings logged and
gated into the v1.0 external-review scope", QUALIFICATION blocker #3.

- **Exists:** `scripts/beta_sim.py` (a *simulated* smoke dry-run of the mechanizable
  exit invariants — at-most-one-solve under concurrency, etc.),
  [`docs/validation/closed-beta-report.md`](../validation/closed-beta-report.md).
- **Do:** run an actual competition with **real external organizers and
  contestants** on the Item-1 deployment. Log findings; triage them into the
  Item-6 external-review scope and a fix backlog.
- **Acceptance gate:** a completed external competition; a findings log; no
  unresolved critical/high issue carried past sign-off. (This is a
  social/operational milestone — it cannot be simulated.)

### Item 4 — Multi-host worker fleet at ≥99% launch

*Closes:* the ≥99%-launch-at-scale half of the operating targets,
QUALIFICATION blocker #4.

- **Exists:** the joined-flow tests prove a **single** launch end-to-end over the
  networked gateway; `scripts/loadtest.py --probe-launch` reports fleet launch
  success as UNVERIFIED until a real fleet exists.
- **Do:** run **multiple** worker hosts against the gateway under the Item-2 load;
  measure launch success across the fleet.
- **Acceptance gate:** **≥ 99 %** instance-launch success sustained across a real
  multi-host fleet at the 25×20 target (folds into Item 2's evidence).

### Item 5 — Continuous RPO measured on the production DB

*Closes:* "Recovery drill: RPO 5min", gate **S8** RPO clause, QUALIFICATION
blocker #5.

- **Exists (mechanism proven):** `deploy/docker-compose.pitr.yml` (WAL archiving),
  `scripts/pitr_drill.sh` + `tests/test_pitr_drill_integration.py` (point-in-time
  restore to a target time; drill RPO window ~3–4 s). RTO already measured by
  `scripts/recovery_drill.sh`.
- **Do:** enable the PITR overlay on the **production** PostgreSQL, ship the WAL
  archive **off-host** (object storage; consider pgBackRest/barman for
  production-grade archiving), and run a real point-in-time restore against a
  production-sized dataset.
- **Acceptance gate:** demonstrated **continuous RPO ≤ 5 min** and **RTO ≤ 30 min**
  on the real deployment/dataset (mechanism is done; this is the *measurement* on
  real infra). See [`docs/operations/backup-recovery-upgrade.md §5`](backup-recovery-upgrade.md).

### Item 6 — Independent external security review

*Closes:* "External security review completed; findings resolved", the v1.0
production-sweep caveats on **S1–S9**, QUALIFICATION blocker #6.

- **Exists:** all S1–S9 evidence is **self-run** in the integration env
  ([`docs/validation/security-checklist.md`](../validation/security-checklist.md),
  [`docs/security/threat-model.md`](../security/threat-model.md)); responsible-
  disclosure policy in [`docs/security/responsible-disclosure.md`](../security/responsible-disclosure.md).
- **Do:** engage an independent firm to assess the **deployed** system (not just
  the repo): authz scoping, container isolation/escape, cross-team access, flag/
  secret leakage, and the control-plane/worker trust boundary. Give them the
  threat model + security checklist as the map.
- **Acceptance gate:** external report delivered; **no open critical/high**; the
  S1–S9 production-deployment sweep signed off against the live system.

### Item 7 — Release-process sign-offs (two)

*Closes:* "Reproducible release artifacts published", "Named internal operators +
rollback plan".

- **7a — Publish versioned artifacts.** Byte-reproducible builds are already proven
  (`tests/test_baseline_fixtures.py`); what's missing is the *publish* action —
  build the versioned `ctfgen` distribution and push it to your index/registry,
  tag the release.
- **7b — Operators + rollback.** Designate named on-call operators and adopt the
  runbooks in `docs/operations/` (esp. [`backup-recovery-upgrade.md`](backup-recovery-upgrade.md)
  and [`docs/security/incident-response.md`](../security/incident-response.md)).
  Rehearse the rollback once.
- **Acceptance gate:** a tagged, installable release exists; a named operator
  roster + a rehearsed rollback are recorded.

## 4. Sequencing

```
Item 1 (deploy TLS + multi-host + storage)  ──┬─▶ Item 2 (capacity 25×20)
                                              ├─▶ Item 4 (fleet ≥99% launch)  ── folds into Item 2
                                              └─▶ Item 5 (continuous RPO on prod DB)
Item 3 (external closed beta)  ── needs Item 1; feeds findings into Item 6
Item 6 (external security review)  ── needs Item 1; ideally after Item 3
Item 7 (publish + operators/rollback)  ── parallel; do before the tag
```

Item 1 is the keystone: capacity, fleet launch, and continuous-RPO measurement can
only be *measured* once a real deployment exists.

## 6. What the client must provide

- Domain name + ability to issue TLS (or an LB that terminates TLS).
- Hosts: control-plane host(s) **and** separate worker host(s) with a rootless
  engine + `NET_ADMIN`.
- Managed PostgreSQL 16 + off-host object storage for WAL/artifacts.
- Real secrets (DB password, `CTFGEN_WEB_CSRF_SECRET`, worker tokens, admin
  bootstrap password) via a secrets manager — never in git.
- An external load-generation environment (out-of-process) for Item 2.
- A contract with an independent security firm for Item 6.
- Real external organizers/contestants for the Item-3 beta.
